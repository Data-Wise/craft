0Objective

Two problems, scoped together because they share root cause and files:

  1. Boundary clarity — the /craft:plan-family (do / orchestrate / plan:*) commands and skills have drifted flags and responsibilities since the planning-refactor spec was written; give them one predictable entry point and unambiguous per-intent ownership.
  2. Dispatch safety — craft's bespoke orchestrate-dispatch background-agent mode was built on an unvalidated token-savings premise, using a mechanism (manual backgrounding) the platform has since made a default, with a safety net (concurrency cap, hang detection) that turns out to be non-enforcing prose. Right-size it against what the platform actually provides today.

Both are informed by four research tracks run 2026-07-04 (§1–§4), combined into one action list (§5).

2Orchestrate-Dispatch Reliability Audit

2.1 Mechanism as designed

orchestrate-dispatch is the third output value of Mode 1 (Spec → ORCHESTRATE), added #240/v2.57.0. Flow: GRILL-file precondition (warn-only) → confirm-before-dispatch AskUserQuestion gate, unconditional even under --yes → dispatch a background Agent with a fixed self-containment prompt: "Read ORCHESTRATE-<topic>.md in full, then execute it." — no other context.

Caps/timeouts today — all prose-level, none executable:

  • Concurrency cap: soft cap of 2 concurrent dispatches per session — an in-context tally the LLM maintains, not a system-enforced semaphore.
  • Hang-detection window: 2 × the ORCHESTRATE file's own stated phase-effort estimate — no fixed constant, no timer.
  • Failure detection: cross-check completion notification against checkboxes. Both hang and failure detection are reports to the user, not kills.
  • Resumability: idempotent re-dispatch driven by the file's own checkbox state — genuinely craft-specific value.

Confirmed by grep: no TaskStop, pkill, pgrep, kill, or timer machinery anywhere in skills/orchestration/. Even orchestrator-resilience's "Timeout / Force terminate / Circuit Breaker" sections are markdown display templates — narrative text, not a syscall.

2.2 Concrete failure modes

  1. Parent session ends/crashes before the background agent completes — nothing tracks or reaps the orphan. Same underlying exposure as the .STATUS 2026-07-04 example (a while true loop, still running 6.5+ hours later). craft's design is somewhat safer (bounded phase-work, not an intentional infinite loop) but has no structural orphan bound.
  2. Hang past the 2×-window produces a report, not a kill. No TaskStop/kill step exists anywhere.
  3. Cross-session interference is real and unguarded. The concurrency cap is per-session — two craft sessions each independently allow 2 dispatches, no shared counter; .STATUS writes race with no locking; worktree paths are deterministic from topic, so same-topic dispatches collide. A v2.57.0 milestone already recorded a near-miss: "recovered a killed agent's completed-but-uncommitted Phase 3 work."
  4. Does the while true leak reproduce identically? No — craft never emits an infinite loop; dispatched work is finite. But the governing property that let that loop leak — persistence with nothing bounding it once the owner is gone — is unaddressed here too.

2.3 Root cause tie-in

The premise for building this mechanism — "save tokens vs. N cold-started sessions" — was never measured (§4), and the platform now backgrounds subagents by default with completion notifications (§3). The custom concurrency-cap/hang-detection layer solves a problem the platform has already absorbed, while providing none of the enforcement it implies.

2.4 Decision: simplify toward platform-native

Drop / shrink

The manually-maintained concurrency-cap tally, the hang-detection wall-clock prose, and orchestrator-resilience's Timeout/Force-terminate/Circuit-Breaker templates — where they overlap platform-native background-agent handling. Replace with: rely on the platform's default background execution and agent_completed/agent_needs_input hooks.

Keep — genuinely craft-specific

The confirm-before-dispatch human gate; the ORCHESTRATE self-containment prompt guarantee; resumability via checkboxes. None of these duplicate a platform default.

Add — the one gap the platform doesn't close

A persistent cross-session dispatch ledger (§2.5) — the platform's defaults are per-session; they don't give visibility into "what did any craft session on this machine dispatch, and is it still alive."

Escalate, don't simulate

A genuine TTL/kill mechanism requires an executable stop at the platform/harness layer. craft cannot guarantee this from inside a markdown skill — recommend asking/filing with the platform rather than faking it with more prose.

2.5 Ledger design

The one net-new piece of craft-side machinery.

  • File: .claude/orchestrate-dispatches.json (project-local, gitignored).
  • Record per dispatch: dispatch_id, session_id, topic, worktree_path, orchestrate_file, dispatched_at, status.
  • Written at dispatch time — every field already exists then, no new logic to produce them.
  • Surfaced via a read-only step in /craft:check (or a small /craft:orchestrate:sweep) listing entries past their expected window — modeled on how /craft:git:clean surfaces orphaned worktrees. Report-only first.

2.6 Documentation gaps to close

  1. State plainly that the caps are LLM-instruction discipline, not runtime enforcement.
  2. Document what happens (today: nothing) if the parent session dies mid-dispatch.
  3. Document the cross-session story: per-session caps, no write-lock, deterministic path collisions.
  4. Add a disclaimer to orchestrator-resilience: its sections are report templates for orchestrator-v2's narrative output, not the dispatch supervisor.

3opusplan / ultracode / Current Platform Capability

Grounded via live research, 2026-07-04.

  • opusplan — a real, current /model value: Opus during Plan Mode, auto-switches to Sonnet once a plan is approved and execution begins. Orthogonal to dispatch-safety.
  • ultracode — a session effort setting (xhigh reasoning + automatic dynamic-workflow orchestration), enabled via /effort ultracode or the keyword in-prompt. Concurrency-capped at 16 concurrent / 1000 total agent calls per run.
  • Directly load-bearing for §2: subagents now run in the background by default (shipped 2026-07-01) — the parent session keeps working, notified on completion. New agent_needs_input/agent_completed hooks exist. Worktree-based background sessions now auto-commit/push/open a draft PR on finishing.

Implication: orchestrate-dispatch (designed pre-2026-07-01) manually implements what the platform has since made a default — the direct evidence behind §2.4.

4Token-Savings Rationale, Verified

The stated reason for building orchestrate-dispatch was avoiding "N cold-started sessions, each reloading CLAUDE.md/system-prompt" — qualitative, never measured, never re-verified since.

  • What it actually credits: dispatching from an already-warm session instead of N fresh terminals. Achievable via a synchronous foreground Agent call too — nothing token-wise is specific to backgrounding.
  • What backgrounding specifically adds: attention/parallelism — not a token claim.
  • The "68.3%" figure measures an unrelated namespace-string tokenization probe — not orchestrate-dispatch.
  • The 60/70/85/90% "compression" figures are context-window-usage trigger thresholds — not tokens saved.
  • Already on record: a related 48% figure is disclaimed as line-count with an "unvalidated" causal link; the real /usage checkpoint (~2026-07-14) is still open.

Conclusion: the token-savings premise for background dispatch specifically was asserted, never measured, and the mechanism it credits doesn't require backgrounding. This doesn't mean orchestrate-dispatch has no value — §2.4 keeps what's genuinely worth keeping, independent of the token claim.

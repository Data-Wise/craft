🧩The Split — you asked to explore it; here's the honest read

After Phase 1 there are ~59 live commands. A 4-way split (core/docs/dist/git) sounds clean but doesn't survive the numbers — dist/ and git/ are too small to justify their own repo, version, and marketplace entry. The only split that pays for itself:

craft-core ~40 live commands · KEEP MONOLITHIC

Daily drivers (do, check, plan, grill, hub, brief, test, orch, done) + code/ (12) + ci/ (8) + arch/ (4) + orch/, plan/, utils/. This is the engineering workflow — it should stay one cohesive plugin.

craft-docs ~19 live commands · THE ONE CLEAN PEEL

docs/ (18) + site/ (1) + the heavy documentation skills (openapi, mermaid, ADRs, site-building). Self-contained, rarely needed mid-code-session, and carries the biggest skills. Installing it separately means a normal coding session never loads doc-tooling into context.

craft-dist / craft-git ❌ NOT worth splitting

dist/ = 2 live commands; git/ already lives entirely in skills/dev/git/. Too thin to carry a repo + version + release cadence. Fold into core.

The real trade-off: a split buys context efficiency (a session loads only what it needs) at the cost of a cross-plugin version dance (shared skills, marketplace entries, two release pipelines). Given you're a solo maintainer, Phases 1–2 may deliver enough that you never need Phase 3. Decide after pruning, with real context-usage data — not now.

🔨 Adverse review — 4 things that bite (sharpest first)

1 · The split does NOT fix the docs pain CATEGORY ERROR

135K lines of docs ÷ 3 plugins = three plugins with ~45K docs each, now with 3× the release/version/test infra. Splitting scatters docs, it doesn't delete them. The lever that reduces docs is native-first thinness (a router needs few docs) + Review #1's dead-doc pruning — both work without splitting at all. Don't sell the split as the docs fix; they're orthogonal.

2 · Monorepo escape is closed → 3 plugins = 3 pipelines COST IS REAL

claude-plugins (the multi-plugin monorepo) is deprecated — craft already migrated out to a standalone repo. So you can't hide 3 plugins behind one shared pipeline the way that repo would have. Three plugins = 3 repos, 3 release pipelines, 3 marketplace entries, 3 test suites, 3 CHANGELOGs. B5's cost objection is live. You've accepted it — but price it with eyes open, and let it argue for 2 plugins, not 3 (fold git into core; it's small + hook-based).

3 · Thin-wrapper rot — native-first cuts both ways MAINTENANCE SHIFT

"Rely on built-in Claude first" trades maintaining a big plugin for chasing Claude's changelog. Claude Code evolves fast; every native skill/tool rename can break a wrapper. Mitigation is the same word as the whole proposal: keep wrappers ultra-thin (route, never reimplement) so there's almost nothing to break, and never bind to internal APIs.

4 · Discovery fragments across plugins UX RISK

Today /craft:* is one namespace with one hub. Split into 3 and the do/hub router — craft's soul — must dispatch across plugins. Verify a craft command can cleanly invoke another plugin's skill before committing; if it can't, the unified ADHD UX fractures into 3 disconnected surfaces.

Recommended sequence — thin FIRST, split SECOND:
  1. Native-first thinning (reversible, high-value): convert Tier-A commands to thin routes to native/plugins — verified per command (the through-line gate). This is what actually cuts docs, and it's safe.
  2. Prune (Review #1): drop the 39 dead-namespace commands; exclude dead docs from the built site.
  3. Then split the now-thin surface into craft + folio (+ maybe warden). Thin plugins are cheap to move; a fat one is not.

Why this order: thinning might shrink the core so much you find you want 2 plugins, not 3 — and you'll never know that if you split the fat version first. Split fat = regret; split thin = trivial.

SPEC-B/ craft-internal planning refactor/ dev

One entry point for planning, one owner per intent

A proposal to give craft's five overlapping planning surfaces — brainstorm, spec capture, strategy advice, artifact generation, and execution — unambiguous routing, without pretending this is a bigger cleanup than it is.

Originated 2026-06-22 Paused 2026-07-04 1 of 8 actions shipped A0 verified
§0 — The actual problem

Why this exists

craft grew several "help me plan something" skills over time, and — because Claude Code activates skills by matching conversation phrasing, not by asking intent first — some of them now compete for the same words.

An earlier framing of this work claimed a ~20-asset consolidation. That was wrong on two counts: it counted planning that actually belongs to sibling plugins, and its own action list added files rather than removing them. This version is narrower and more honest: it's not about fewer files. It's about routing disambiguation — making sure that when someone says "plan a sprint," exactly one skill knows that's its job.

Scope boundary

Cross-plugin domain planning was split out to a separate spec (SPEC-A). This proposal covers craft-internal, generic-software planning only.

§4–5 — Proposed architecture

The pipeline

Two intents live on one axis — deliberate vs. act — and each tier of deliberation gets exactly one owner:

tier 1
brainstorm
→
tier 2
spec capture
→
tier 3 · strategy
project-planner
→
tier 4 · artifact
plan-orchestrator
↓ one-directional hand-off at the seam ↓
tier 5 — execute
/craft:do → complexity router → command / agent / orchestrator

/craft:plan would own tiers 1–4: it produces a durable SPEC-*.md or ORCHESTRATE-*.md file, then stops. It hands that artifact to /craft:do exactly once, and never the reverse — /do may suggest planning on high-uncertainty intent, but never invokes it. One seam, one direction.

§14 (spec) — A0 verdict

A0: does superpowers actually preempt craft?

Verified 2026-07-04 — real, but scoped

superpowers ships its own SessionStart hook (matcher startup|clear|compact) that unconditionally injects the full using-superpowers skill body as <EXTREMELY_IMPORTANT> context on every top-level session start — regardless of task type. That body asserts "'Let's build X' → superpowers:brainstorming first, then implementation skills", with zero awareness of craft's own skills/workflow/brainstorm, which shares nearly the same trigger vocabulary. The collision is genuine.

Two mitigants, found via a live subagent test: (1) enforcement is prompt-level only — the actual PreToolUse hooks in settings.json (branch-guard, version-sync-hook, no-switch-guard, rtk) don't gate Write/Edit on prior skill invocation, so nothing technically blocks implementation before brainstorming runs. (2) it does not propagate to subagents — a freshly dispatched agent's context held only the bare name superpowers:using-superpowers, not its injected body, so craft's own orchestrate-dispatch/plan-orchestrator background-agent work (where most real implementation happens) is untouched.
